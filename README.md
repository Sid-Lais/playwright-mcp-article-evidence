# Playwright MCP measurements: evidence for the article

Evidence repo for *"Playwright MCP for Test Automation: What It Does Well and Where It Breaks"*.
Everything here is runnable. **No LLM is involved in any measurement**: the harness calls the MCP
server's tools directly through the MCP TypeScript SDK, so the numbers describe the server's output only.

## Provenance (read this first)

This harness and its three pages were assembled on 2026-11-01 as a clean, pinned re-run of the experiment
described in the article. The numbers below come from that re-run, not from the original session
logs. Where they differ from the article, the delta is listed in [Article vs. re-run](#article-vs-re-run).
There are no AI prompts in the measurement path (no model is in the loop), so there are no prompts to
publish for the tests themselves.

## Installation

```bash
npm ci
npx playwright-core install chromium
```

How the MCP server is obtained: it is an npm dependency pinned to `0.0.83` and launched by
`scripts/run.ts` as `node node_modules/@playwright/mcp/cli.js ...` over stdio. The article's
`claude mcp add playwright npx @playwright/mcp@latest` command is the setup from the official README and
was not used for these measurements (the harness is its own MCP client).

## Reproduce

```bash
npm run measure      # tokens, ref counts, timings, generated Playwright code  -> results/
npm run claims       # checks flags/tools/args the article states               -> stdout
npm test             # visibility-assertion behaviour on the checkout page
npm run chart        # regenerates results/tokens-chart.svg from results/summary.json
```

All-caps tool count: `npx tsx scripts/run.ts --caps=config,network,storage,devtools,vision,pdf,testing`
(output saved in `results/run-all-caps.log`, `results/summary-all-caps.json`).

## Layout

| Path | What |
|---|---|
| `pages/login.html`, `pages/products.html`, `pages/checkout.html` | The three local test pages. `products.html` is generated by `scripts/gen-products.mjs` |
| `scripts/run.ts` | MCP client harness. Starts a static server, launches the MCP server, calls tools, records raw responses, latency, token counts |
| `scripts/claims.ts` | Verifies secondary claims (arg names, flags, caps) against the pinned server |
| `tests/hidden.spec.ts` | Playwright Test file that checks which assertions pass on the hidden checkout messages |
| `results/*.txt` | Raw, unedited tool responses (one file per call) |
| `results/summary.json` | Per-call latency, tokens, ref counts |
| `results/tools.json` | Full tool definitions returned by `tools/list` |
| `scripts/chart.ts`, `results/tokens-chart.svg` | Token bar chart, rendered directly from `results/summary.json` (no hand-entered numbers) |

| Login snapshot | 354 tokens full response (308 for the YAML block), 19 refs |
| Product list (60 cards) snapshot | 9,972 tokens full response (9,937 for the YAML block), 483 refs |

### The brittle locator

Calling `browser_click` on the 3rd of 60 identical "Add to cart" buttons returns (raw: `results/products-click-add-3.txt`):

```js
await page.getByRole('listitem').filter({ hasText: 'Trail Shoe Model 3 $43.99' }).getByRole('button').click();
```

The price is part of the locator. Changing the price in `pages/products.html` (card 3, `$43.99`) breaks it.

### How the failure state is created

There is nothing to tune: the generated locator embeds the card's visible text. The "failure" is the
price in the card changing from `$43.99`; edit the price in `scripts/gen-products.mjs`, regenerate, and the
recorded locator no longer matches.

### Hidden UI

`pages/checkout.html` has `#drawer` (`position: fixed; right: -400px`) containing "Order confirmed" and
`#errors` (`height: 0; overflow: hidden`) containing "Payment declined". Raw snapshot: `results/checkout-snapshot.txt`
shows both as present. `npm test` result on the pinned Playwright version:

| Assertion on the hidden message | Result |
|---|---|
| `toHaveText(...)` | passes (false pass) |
| `toBeVisible()` | **also passes**: Playwright treats any non-empty box as visible, regardless of off-screen position or clipping |
| `not.toBeInViewport()` | passes, i.e. `toBeInViewport()` is the assertion that fails |

### Verified secondary claims (`npm run claims`, output in `results/claims.log`)

- `browser_click` takes `target`; the legacy `ref` argument is rejected with a schema error.
- `browser_find`, and `browser_snapshot` with `target`/`depth`, exist in core.
- `--snapshot-mode=none` removes the snapshot from responses.
- `--caps=testing` adds `browser_generate_locator` and four `browser_verify_*` tools. `browser_generate_locator` on the 3rd "Add to cart" button returns the same price-dependent locator: `getByRole('listitem').filter({ hasText: 'Trail Shoe Model 3 $43.99' }).getByRole('button')`.
- `file://` URLs are blocked by default, so the harness serves pages over local HTTP.
- `--allowed-origins` blocks navigation to non-listed origins. The package README states it
  "does not serve as a security boundary and does not affect redirects".

## Article vs. re-run

| Article | Re-run | Note |
|---|---|---|
| 25 core tools | 25 | match |
| 4,396 tokens of tool definitions | 4,396 | exact match |
| Login snapshot 276 tokens | 354 (308 YAML only) | different page markup |
| Product list 10,720 tokens, 487 refs | 9,972 (9,937 YAML), 483 refs | different card markup |
| Locator filters on "Trail Shoe Model 3$43." | "Trail Shoe Model 3 $43.99" | different card markup |
| Snapshots under 100 ms | 10 to 114 ms | machine load dependent |

Page markup for the originals is not reproduced here; the per-card ref count in this repo
(8 per card x 60 + 3 page-level = 483) is a direct function of the markup.
